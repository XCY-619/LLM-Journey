## 阶段 2：Function Calling（工具调用）底层剖析

### 一、 核心概念与问答沉淀

#### 1. 工具匹配与决策机制
* **我的疑问**：如果修改工具的 `description`（描述），大模型还会调用它吗？
* **正确理解**：**不会**。大模型通过 Transformer 注意力机制将用户提问与 `tools.description` 进行语义匹配。若修改后语义不匹配，模型将放弃调用工具，直接退回普通聊天模式。
* **边界补充**：传入 `tools` 不代表**一定会**触发中间过程。若模型评估自身知识足以回答（如“1+1等于几”），首轮请求即直接输出文本（`finish_reason='stop'`），无需跑腿。

#### 2. 无状态（Stateless）与对话串联
* **我的疑问**：看似连续的工具调用对话，在大模型视角下是不是完全独立的多次 HTTP 请求？
* **正确理解**：**完全正确**。大模型本身没有任何长历史记忆，它是完全无状态的。
  - **请求 1（决策）**：发送（问题 + 工具说明书） $\rightarrow$ 模型决策输出 `tool_calls` 指令（附带唯一标识 `tool_call_id`），云端计算结束并归零。
  - **本地执行**：Python 代码解析指令，在本地电脑运行真实函数拿到结果。
  - **请求 2（总结）**：Python 将 `[1. 用户问题, 2. 模型指令, 3. 本地结果]` 打包为**全新请求**塞给大模型 $\rightarrow$ 模型读取全量历史并总结为自然语言。
* **核心洞察**：所谓的“连续对话”，本质是本地 Python 代码通过 `messages` 列表不断把完整的历史记录重新打包塞回给大模型。

#### 3. 数据结构与调用模式
* **消息格式**：`{"role": "xxx", "content": "yyy"}` 中，`role` 标识身份（`user` / `assistant` / `tool`），`content` 承载具体文本。当模型发工具指令时，`content` 可为空，关键信息在 `tool_calls` 结构体中。
* **并行 vs 串行**：大模型支持并行工具调用（单轮请求同时给出多个 `tool_calls` 指令）；只有后一步依赖前一步结果时，才会产生多轮串行中间过程。

## 阶段 3：ReAct 自动循环引擎 (Agent Engine)

### 一、 核心机制与架构设计
1. **`while` 自动化驱动**：以 `finish_reason` 为状态切换依据：
   - `tool_calls`：解析指令 $\rightarrow$ 运行本地函数 $\rightarrow$ 追加 `role='tool'` 记录 $\rightarrow$ 自动触发下一次请求。
   - `stop`：决策收敛，提取最终回答，退出循环。
2. **解耦路由 (`TOOL_MAP`)**：用字典将字符串函数名映射为真实 Python 函数，配合 `**func_args` 字典解包，实现扩展新工具时引擎零修改。
3. **工程安全熔断 (`max_steps`)**：显式设置最大循环阈值（如 `max_steps=5`），防止 Prompt 歧义或逻辑异常导致无限死循环。

### 二、 并行与串行工具调用
- **并行调用（1 轮循环解决）**：当子任务互相独立（如“查时间 + 做计算”）时，模型在单次 `tool_calls` 中同时下达多个指令，循环体执行完所有工具后一次性提交给模型。
- **串行调用（多轮循环推进）**：当子任务存在依赖链（如 `(A+B)+C`）时，模型通过多轮 `while` 循环，逐步拿到中间结果并推进推理。
